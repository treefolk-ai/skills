# Capture a UI component description

## Outcome

将多轮、零散的 UI 设计输入整理成一个组件一份、可审阅且可交接的 Markdown 设计描述。最终文档包含组件结构、规格、状态、信息来源、待确认项和 ASCII 预览；仅在输出路径和写入意图都得到明确确认时写入文件，不生成组件实现代码。

## Use when

- 用户准备逐步提供同一个 UI 组件的 Figma Inspect、CSS、尺寸、文案、交互、状态或截图。
- 用户希望边补充、边整理、边发现关键缺口，直到明确说“完成”。
- 用户需要一份可交给设计、开发或其他工作流继续使用的组件级设计描述。
- 用户要求把零散设计证据沉淀为一个组件一个 Markdown 文件。

## Do not use when

- 用户要直接实现或修改组件代码。
- 用户已经有完整规格，只需要实现、视觉审稿或验收现有页面。
- 用户只询问一个 CSS 属性、一个截图细节或一次性排版建议。
- 用户需要页面级产品方案、完整设计系统或跨组件信息架构，而不是单组件描述。

## Inputs

- 必需：至少一项与当前组件有关的设计证据，例如文字说明、Inspect、CSS、尺寸、文案、状态、交互、截图或其他可访问视觉输入。
- 可选：组件名、项目或方案名、目标读者、输出路径、已有设计描述、期望保留的原始片段。
- 默认：一次只整理一个组件；缺少名称时使用明确标注的临时名；先在对话中维护累计草稿；没有明确写入授权时不写文件，即使用户之前提供过路径。

## Preconditions

- 确认当前输入属于哪个组件；若无法判断，先询问一个区分问题。
- 若已有草稿或目标文件，先读取内容，判断是继续同一组件还是可能覆盖其他工作。
- 将每条信息标记为 `用户确认`、`来源原文`、`截图推断` 或 `待确认`，不要把推断升级为事实。
- 最终整理前读取 [references/output-template.md](references/output-template.md)。
- 写文件前确认目标仓库、仓库内的 POSIX 相对路径、组件文件名以及用户的写入意图；解析目标后确认它没有通过符号链接逃离用户选定的工作区。

## Workflow

1. 建立当前组件记录。保存正式名或临时名、使用场景、目标读者、证据来源和已确认的输出位置；不要因为缺少非关键字段而阻塞首次整理。
2. 识别本轮输入类型，将内容归入结构、布局、尺寸、间距、视觉、文本、图标、文案、交互、状态、设计 token、截图观察或原始证据。只保留与当前组件直接有关的页面上下文。
3. 归一化表达但保留来源原意。例如把 `display`、`flex-direction`、`justify-content`、`align-items`、`gap`、尺寸、间距、背景、边框、圆角、阴影和字体属性放入相应规格字段；不要擅自改变用户给出的数值或字重策略。
4. 合并累计草稿。用户明确提供的值优先于截图推断；新的明确修订可以替代旧值，但要记录变更。来源互相冲突、组件归属不清或会影响实现的关键值缺失时，一次最多问 3 个最关键问题；相关缺口合并成一个问题，不得用多个列表项绕过上限。
5. 每轮返回四部分：本轮新增或修订的已确认信息、最多 3 项最关键的待补充信息、当前累计规格摘要、当前 ASCII 结构预览。重复输入没有改变草稿时，明确报告 no-op 并继续等待下一项证据。
6. 用户切换到另一个组件时，不要合并记录。先确认是暂存当前组件、完成当前组件，还是开启一份新的组件描述。
7. 仅在用户明确表达“完成”“输出最终版”“生成描述文档”或“写入文件”时结束收集。按参考模板生成最终文档：
   - 已确认路径时，先检查现有文件；只有能证明它属于同一组件且更新意图明确时才写入。
   - 未确认路径时，在对话中交付完整 Markdown，并报告尚未落盘。
   - 用户要求写入但缺少项目目录或稳定文件名时，只询问缺失的路径信息，不自行翻译、拼音化或猜测。
8. 对照全部输入验证最终文档，重新读取已写文件，并报告未解决问题、推断内容和未执行的实现工作。

## Stop conditions

- 无法判断输入属于哪个组件，或多个组件的信息无法安全拆分。
- 明确来源之间存在会改变结构、状态或关键规格的冲突。
- 关键视觉输入无法读取，并且缺失内容不能通过用户描述安全补足。
- 用户要求写文件，但目标路径、组件文件名或写入授权不明确。
- 目标文件似乎属于其他组件，或写入会覆盖无法证明可替换的内容。
- 目标路径位于用户选定工作区之外，或通过无法确认安全的符号链接解析到其他位置。
- 输入包含疑似凭据、私密链接、无关内部数据或其他不应复制到设计文档的信息。

## Safety

- 不实现组件代码，不修改应用源码，也不把设计建议伪装成已确认规格。
- 不臆造像素值、颜色、字体、状态、层级、交互或响应式行为；未知内容保持 `待确认`。
- 将截图结论标记为 `截图推断` 并附置信度；用户确认值与截图冲突时，以用户确认值为准并记录冲突。
- 将工作设计材料视为可能保密的数据；不要上传到网络、转发到外部服务或复制无关项目上下文。
- 不把凭据、私密 URL、用户数据或无关内部标识写入最终文档。发现疑似敏感内容时停止并只报告其位置和类型，不回显值。
- 不覆盖不相关文件。只在用户确认的工作区和目标路径内创建或更新文档。

## Verification

- 确认最终产物只描述一个组件，并且名称、结构、规格、状态和交互与累计输入一致。
- 抽查每个精确数值和关键结论都能追溯到用户确认、来源原文或明确标记的截图推断。
- 确认最终文档包含组件信息、结构、设计规格、状态与交互、证据来源、待确认项、ASCII 预览和交接摘要。
- 确认没有用虚构值填满缺口，没有混入实现代码或另一个组件的信息。
- 若写入文件，重新读取目标文件，确认路径、内容和组件身份正确，并检查没有覆盖未授权内容。
- 若未写入文件，明确验证交付的是完整 Markdown，并将落盘标记为未执行而不是成功。

## Completion report

报告组件名称、交付方式（对话或文件）、文件路径（如有）、采用的证据类型、已标记的截图推断、仍待确认的事项，以及是否发生 no-op 或部分完成。明确说明没有实现组件代码，也没有执行未经授权的文件写入。
