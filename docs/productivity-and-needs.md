# 生产力如何改变需求

> 生产力的提升，会改变你能够遇见的问题，进而改变你能够理解的需求。

这个心得来自我在开发和使用 AI 过程中的三个具体变化：

| 工作状态的变化 | 随之浮现的需求 |
| --- | --- |
| 以前没有足够的生产力同时开发多个 Git 仓库，后来开始维护多个仓库 | 开始考虑用 eza 之类的工具，更方便地浏览仓库目录、辨认状态和切换项目 |
| 以前没有维护多个 npm 包的需求，后来开始面对多个包及其关系 | 开始在意 monorepo 和 pnpm workspace 这样的组织方式 |
| 以前没有并行多个 Codex 项目，后来开始同时推进多个项目 | 开始讨论跨项目共享记忆，希望减少重复解释、复用经验并保持一致性 |

这些工具和话题进入我的视野，都与工作状态的变化有关。能够完成更多工作之后，我开始遇到新的摩擦，也终于有了理解相应工具价值的具体经验。

**需求会随着工作方式生长。**

我们常把需求理解为一个已经存在、等待被发现和解决的问题。这几个经历提示了另一种可能：能力提升让人进入新的工作状态，新需求也会在那个状态中形成。

其中可能同时发生两件事。有些需求原来就存在，只是受限于能力，暂时顾不上；有些需求则需要新的工作方式才能成立。单个项目里，我可能希望 AI 记住偏好。多个项目并行之后，才会进一步关心：哪些经验应该共享，哪些约定只属于当前项目，一个项目里纠正过的错误能否少在另一个项目里发生。

这意味着，提升生产力的工具，也可能参与创造下一批工具的需求。提前询问一个尚未进入这种工作状态的人，未必能得到完整答案；亲自完成更多事情，会让原本模糊甚至尚未形成的问题变得具体。

**工作数量增加之后，事物之间的关系也开始需要维护。**

只有一个仓库、一个包或一个项目时，注意力主要放在它内部。数量和并行程度提高后，切换、依赖、一致性、优先级和经验复用开始占用精力。

多个仓库需要定位和辨认；多个包需要处理共享代码与变更影响；多个 AI 项目需要决定上下文如何保留、隔离和复用。每一次协调可能都很小，反复发生后就会形成持续的负担。

因此，执行能力变强之后，人可能更需要整理、命名、约定和记忆。过去限制进展的地方可能是做不出来，后来可能变成同时发生的事情太多，很难一直保持清楚。每当执行成本下降，都值得观察注意力随后花在了哪里：那里可能正在出现下一批需求。

**理解工具的价值，有时需要先获得相应的经历。**

知道一个工具存在，与理解它为什么值得使用之间，可能隔着一段真实的工作经历。经历过连续切换仓库、检查多个包的变更影响、反复解释同一段背景之后，工具的功能才有了可以对照的具体问题。

过去没有采用某个工具，可能完全符合当时的工作状态。它带来的收益还很小，学习、配置和维护成本却已经存在。后来觉得它有价值，是因为使用条件发生了变化。评价过去的选择，也应该考虑当时的规模、频率和负担。

工具介绍因此可以从用户能够认出的处境开始。例如，“同时维护多个项目，切换时总要重新解释背景”，能让经历过这件事的人直接理解价值。抽象的能力名称需要读者自己补上这段联系。

**新增的管理需求，也值得重新判断。**

生产力增加，让更多尝试成为可能；新的复杂度是否值得保留，仍然需要选择。多个仓库可能承载持续有价值的工作，也可能包含已经不再推进的尝试。共享记忆可以减少重复，也可能把过时的偏好和局部约定带到其他项目。

面对反复出现的摩擦，可以投入工具改善管理，也可以减少同时推进的事情。判断依据是这个摩擦出现的频率、它影响的工作是否值得继续，以及解决之后能否更轻松地做自己在意的事。能力增长提供了选择空间，如何使用这个空间仍然属于自己。

**这个观察为 Treefolk Skills 的成长提供了一条线索。**

这个项目已经在 [DESIGN.md](../DESIGN.md) 中把真实、反复出现的用户目标作为工作流的来源。这份心得补充了一个寻找它们的视角：

> 最近我因为能够做更多事情，开始反复处理什么以前不会遇到的麻烦？

产出增加后，可能更需要统一检查和收尾；项目增加后，可能更需要恢复上下文和判断下一步；与 AI 反复协作后，可能更需要保留纠正，让同样的问题少发生一次。这些具体经历可以成为改进工作流的材料。

等到任务边界清楚，再依照现有的产品准入规则，判断它适合进入已有 skill、成为内部步骤或脚本，还是值得拥有一个独立入口。工作流库可以随着真实使用逐步成长，让名称、描述和默认路径贴近用户已经能够认出的处境。

还有一个值得继续观察的方向：能力提升除了改变我需要什么，也可能改变我想做什么。当原本难以完成的事情变得可行，新的项目、协作方式和安排才会进入选择范围。以后记录类似经历时，可以同时留下能力发生了什么变化、第一次遇到了什么摩擦，以及它如何改变了自己的选择。
