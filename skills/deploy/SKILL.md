# Deploy a project

## Outcome

Deploy one reviewed source state or build artifact to one exact existing hosting target, defaulting provider selection to Cloudflare only when no provider is named and project evidence does not conflict, then verify the result against both authoritative provider state and the intended live endpoint. If the exact candidate is already the active healthy deployment, return a successful no-op. Preserve and report independently verified local, build, and remote progress when the complete outcome cannot be confirmed.

## Use when

- The user explicitly invokes `$deploy` to publish or update a ready application, site, service, or worker.
- A Cloudflare deployment should use an existing project, service, environment, and deployment configuration.
- An explicitly named non-Cloudflare provider has a complete project-owned deployment path that can satisfy this same safety and verification contract.
- The user invokes `$deploy plan` to inspect the local deployment plan without building, accessing the network, or changing local or external state.

## Do not use when

- The user has not explicitly invoked `$deploy`; deployment changes an external system and must not be selected implicitly.
- The requested outcome is only a Git commit, push, initial repository publication, or pull request; use the corresponding Git workflow.
- The work is to create or configure a hosting account, project, service, environment, domain, DNS record, route, secret, binding, database, storage resource, or CI/CD pipeline.
- The request is only to inspect status or logs, diagnose a failed deployment, roll back, delete, or migrate hosting infrastructure; handle that narrower lifecycle task separately.
- In normal mode, the project is not yet prepared to validate and deploy the selected source state or artifact with already available, trusted tooling. `$deploy plan` may still inspect static project evidence and report the missing preparation.

## Inputs

- Required for a real deployment: an explicit `$deploy` invocation and one exact existing provider account, project or service, product type, environment or stage, and source or artifact. These values may come from the current invocation or unambiguous project and provider evidence; they are not optional merely because Cloudflare is the provider default.
- Optional: target directory, provider, provider account, provider product including Cloudflare Pages or Workers, project or service name, environment, production or preview intent, source revision, artifact path, build and deploy commands, expected route or URL, and a non-mutating health or smoke check.
- Optional mode: `plan`, invoked as `$deploy plan`.
- Defaults: current directory; provider `cloudflare` only when project evidence does not conflict; the repository-owned build and deploy workflow; the single project-configured default target when its product, account, project, environment, and traffic effect are all unambiguous; current reviewed source state; and at most one reviewed provider deployment operation.
- A normal-mode `$deploy` invocation authorizes one normal deployment to the resolved existing target with its already-reviewed configuration. The only permitted traffic effect is advancing that target to the candidate under its unchanged existing traffic policy. It does not authorize target creation, production selection when no default is configured, login or account switching, tool installation, Git publication, routing, domain, traffic-policy, secret, or binding changes, migrations, rollback, deletion, or another provider-mutating retry.
- `$deploy plan` authorizes local read-only inspection only. It does not authorize a build, network access, file changes, command execution that may write or contact a service, or any external mutation.
- An explicitly named provider overrides the Cloudflare default. Never fall back to Cloudflare after an explicit provider fails, and never replace a clearly configured non-Cloudflare workflow with Cloudflare merely because no provider was written.
- There is no default for Cloudflare Pages versus Workers, account, project or service name, environment, production versus preview, route, domain, build command, output directory, or health endpoint.

## Preconditions

- Determine `plan` versus normal mode first. In `plan` mode, inspect only static local files and use filesystem or Git queries proven not to write; set `GIT_OPTIONAL_LOCKS=0` when Git inspection is needed. Do not invoke a provider CLI, package manager, project script, or command that may write caches or configuration, check for updates, emit telemetry, or access the network. Mark information that cannot be established under these constraints as unresolved.
- Resolve the physical target directory and applicable repository instructions before changing anything. Inspect deployment documentation, manifests, lockfiles, package scripts, build configuration, hosting configuration, and existing deployment scripts.
- Record the Git repository and exact source state when present: branch, commit, staged and unstaged changes, and relevant untracked files. When building from source, determine which files and generated inputs the candidate build would include; when deploying an existing artifact, establish its origin and identity without requiring an unnecessary rebuild. Do not commit, push, switch branches, or clean the worktree.
- Select the provider from explicit input or the Cloudflare default, then resolve one product, authenticated account, existing project or service, environment, traffic effect, and deployment command. Treat conflicting provider configuration as ambiguity, not permission to migrate it.
- For Cloudflare, distinguish Pages, Workers, and any other product only from explicit input, a repository-owned command, Cloudflare configuration, or authoritative provider metadata. Do not infer the product from the framework or output directory alone.
- In normal mode, prefer a repository-owned deployment command and project-pinned tooling. Otherwise require an already installed provider CLI whose version and relevant help can be inspected without downloading or upgrading it. Review the complete command chain of any wrapper or project script; one outer command is not evidence of one provider mutation. Do not use a command that may implicitly fetch a CLI or dependencies.
- In normal mode, verify the active authenticated provider identity and query the exact target before building or deploying. Distinguish confirmed absence from authentication, authorization, connectivity, rate-limit, and indeterminate failures. A missing target is a stop condition, not permission to create it.
- Inspect the candidate configuration, source inputs, deploy manifest, dry-run or bundle description when locally available, and artifact file list for credentials, private keys, `.env` or `.dev.vars` data, local databases, logs, debug material, and unexplained large or generated files. Do not print secret values.
- Before any provider mutation, require a provider-supported plan, dry-run, configuration diff, or equivalent evidence that can compare the complete planned operation with the target's authoritative current configuration. First enumerate every external surface the selected configuration and complete command chain can modify; compare each referenced surface, including any routes, domains, environment settings, traffic policy, bindings, secrets, storage, databases, or migrations, and prove that unreferenced surfaces are outside the command chain. If the provider does not expose enough state for a referenced surface, or the evidence cannot prove that the only external delta is the candidate code or artifact and its activation under the unchanged policy, do not deploy. This proof is not required merely to recognize and verify an already-active candidate without mutation.
- Identify the repository-required validations, the build command and toolchain only when the selected input must be built from source, and a bounded, non-mutating live check. For an existing artifact, identify the applicable integrity, provenance, and content checks and rebuild it only when repository policy requires that. Require the applicable prepared local tooling to be available; do not install or upgrade tools or dependencies as part of the default workflow.

## Workflow

For steps 1–4, `plan` mode accumulates safely discoverable conflicts and missing values as unresolved plan blockers and continues static local inspection where safe; normal mode stops immediately on those blockers.

1. Resolve the provider. Honor an explicit provider. Otherwise select Cloudflare only when that does not conflict with the project's existing deployment configuration. If the project clearly targets another provider, require an explicit provider choice rather than migrating or overriding it.
2. Resolve one exact deployment identity: provider, product, sanitized account identifier, existing project or service, environment or stage, production or preview effect, and expected routes or URLs. Prefer explicit input, then one unambiguous project-owned configuration. For Cloudflare, never choose between Pages and Workers by guesswork. Treat any value that changes the destination or traffic effect as a blocker when it remains ambiguous.
3. Select the execution path. In `plan` mode, inspect only static project documentation, configuration, and script text; record the declared command chain without executing it, and leave CLI capability and remote state unresolved. In normal mode, prefer the project's documented deploy script, then a project-pinned provider CLI invocation, then an already installed CLI only when its inspected version and help support an exact non-interactive command; review the complete nested command chain and planned provider operations. If the project uses a Git-triggered deployment, query an already triggered deployment for the exact published commit; do not commit, push, merge, or create a pull request to trigger it. When the exact expected deployment is already running, reserve it for bounded read-only monitoring instead of triggering another; stop on an unrelated, competing, or unattributable in-progress deployment. When no deployment exists for the required published commit, stop normal mode at the missing Git publication boundary rather than falling through to a direct provider operation.
4. Identify the candidate source or artifact and classify how local worktree state relates to it. For a direct source deployment, review every included staged, unstaged, and untracked change and continue only when each one is understood and belongs to the requested deployment. For a Git-triggered deployment, require one exact published commit and prove that local dirty or untracked files are not inputs to the remote candidate; leave and report them without treating their mere presence as a blocker. For an existing artifact, prove its identity and provenance independently and treat local changes as blockers only when they can affect that artifact. In normal mode, stop when the candidate boundary remains unclear without stashing, cleaning, committing, or excluding files by guesswork. In `plan` mode, record the unclear source scope as a blocker and continue only the remaining safe static inspection.
5. In `plan` mode, report the locally provable provider, product, target clues, source state, proposed validation, build, deploy, and verification commands, expected external mutations, unresolved values, and stop conditions. Do not run builds, access provider or live endpoints, install anything, change files, or claim deployability or remote readiness; then finish.
6. In normal mode, query the provider's current target state and record its deployment or version identity, status, source metadata, environment, routes or URLs, and update time. If the exact candidate is already in progress, monitor it read-only for a bounded period and continue to verification only if it reaches a confirmed terminal success; report its terminal failure or a still-running timeout without triggering another operation. If authoritative evidence proves that the exact candidate is already active, terminate without another deployment: return a successful no-op when the safe live check passes; report `failed` with the existing deployment active but unhealthy when it fails; or report `partial completion` with remote state verified and live verification unavailable when no safe check exists. Do not infer equivalence from similar timestamps, names, or a clean Git worktree.
7. Prepare the candidate. For source input, run the required local validations and build with the prepared, repository-declared toolchain. For an existing artifact, run the applicable integrity, provenance, and content checks and do not rebuild unless repository policy requires it. Preserve lockfiles and configuration. Review the final artifact or provider bundle description and confirm that its path, contents, size, and source identity match the resolved target and contain no suspected secret or unrelated output. Obtain the provider plan, dry-run, configuration diff, or equivalent evidence; enumerate every external surface referenced by the selected configuration and complete nested command chain; and compare those surfaces with authoritative current target configuration. Prove that unreferenced surfaces are outside the command chain and require the only planned change to be the candidate code or artifact and its activation under unchanged target configuration. Stop before deployment on any failed or unrun required check, any referenced surface the provider cannot reveal well enough to compare, or any unprovable or out-of-scope delta.
8. Re-query the exact provider target immediately before mutation and record its current version as the deployment precondition. Stop if the active deployment, configuration, environment, routes, or concurrent activity changed in a way that invalidates the reviewed plan. Use an expected-current-version, ETag, deployment lock, or other conditional update when the provider supports one. When no atomic guard exists, minimize the query-to-mutation window and disclose the remaining concurrency limitation. Treat concurrency as plausible only when there is concrete evidence such as an in-progress or recent unrelated deployment, an active shared CI trigger, a repository serialization rule, or another known writer; theoretical remote mutability alone is not a blocker.
9. Run one reviewed, non-interactive provider deployment operation against the exact target. A wrapper or project script is acceptable only when its complete command chain contains that one deployment operation and no other external mutation. Pass account, project or service, environment, artifact, and production or preview intent explicitly when the chosen command would otherwise prompt, infer, or use an unsafe ambient default. The only allowed traffic change is advancing the resolved target to the candidate under its unchanged existing traffic policy. Refuse prompts to log in, switch accounts, create resources, install tools, or expand the mutation beyond the reviewed deployment.
10. After any success, failure, timeout, or interrupted response, first determine whether the local command has ended or may still be running, then observe authoritative provider state for a bounded period until the correlated deployment is terminal or state is stable. Correlate the candidate with a deployment or version identifier, source or artifact identity, creation time, environment, status, and URL. Do not issue a second provider-mutating operation in the same invocation. If attribution remains indeterminate, report that the provider operation may still complete and change external state later, and require a fresh provider-state audit before any future attempt.
11. For a confirmed deployment, verify that it is active on the intended target and run the bounded non-mutating check against the provider URL or configured endpoint. Check the expected status and a project-defined version or content marker when available. Do not exercise state-changing application actions. If the endpoint is intentionally private or no safe live check exists, state the exact verification limitation instead of inventing one.
12. Reinspect the local source and generated files, then report success, no-op, partial completion, indeterminate attribution, or failure from the evidence actually obtained. Do not roll back a deployment automatically when verification fails.

## Stop conditions

A missing explicit invocation or an inability to continue local inspection safely stops either mode. In normal mode, every other condition below stops the workflow before further action. In `plan` mode, record it as an unresolved blocker and continue only safe static inspection, then report `local plan only` rather than a failed deployment attempt.

- `$deploy` was not invoked explicitly, or the request does not authorize a real deployment or the requested `plan` mode.
- Provider configuration conflicts; the provider product including Pages versus Workers on Cloudflare, account, project or service, environment, production or preview effect, candidate source or artifact, or execution path is missing or ambiguous; or the selected product and traffic effect require a route or URL that remains unresolved.
- The exact target does not already exist, the authenticated account is unavailable or unexpected, or provider lookup cannot distinguish absence from an authentication, authorization, connectivity, rate-limit, or indeterminate failure.
- Required tooling or dependencies are unavailable, untrusted, would need installation or upgrade, or the only proposed command may download them implicitly.
- The candidate source is unclear, unrelated work would enter the deployment, the Git-triggered source has not been published, or a suspected secret or unsafe file may be bundled or uploaded.
- A required validation or build fails, the artifact cannot be identified and reviewed, or the locally produced result does not match the configured deployment input.
- The complete command chain or planned provider delta cannot be inspected, would perform more than one deployment operation, or would create or modify an account, project, service, environment, billing setting, domain, DNS record, route, secret, binding, database, storage resource, migration, access policy, or other infrastructure outside one normal deployment.
- Provider state changes after preflight, an unrelated, competing, or unattributable deployment is in progress, repository or provider policy requires concurrency protection that is unavailable, concurrent activity remains plausible without a guard, the mutation result remains indeterminate, or the resulting deployment and live state cannot be verified.

## Safety

- Never log in, switch accounts, expose credentials, install or upgrade CLIs or dependencies, or accept an interactive fallback as part of the default workflow.
- Never create or delete hosting resources or alter billing, domains, DNS, routes, traffic weights, rollout rules, traffic policy, secrets, bindings, storage, databases, migrations, or access policy. Advancing the resolved target to the candidate under its unchanged existing traffic policy is the only default external mutation.
- Never commit, amend, push, merge, rebase, reset, switch branches, create a pull request, rewrite history, clean the worktree, or change source or deployment configuration merely to make deployment proceed.
- Never upload `.env`, `.dev.vars`, credentials, private keys, local databases, logs, unrelated build output, or an artifact whose contents have not been reviewed. Do not reveal secret values in commands, logs, reports, URLs, or screenshots.
- Never guess Cloudflare Pages versus Workers, production versus preview, an account, project, service, environment, output path, or domain. Never silently change providers or use an unrelated ambient default.
- Never delete, roll back, purge, retry, or deploy to a fallback target after a failure unless a later explicit request separately authorizes that operation. Do not treat automatic provider rollback as verification of the intended outcome.
- Never claim deployment success from a command exit code, upload completion, generated URL, or HTTP response alone. Require correlated authoritative provider state and the applicable live check.

## Verification

- Confirm the final provider, product, sanitized account, project or service, environment, and production or preview effect match the resolved target.
- Query the provider after the attempt and verify the deployment or version identifier, status, source or artifact identity when available, creation time, active target or traffic assignment, and canonical URL. Confirm that the reviewed configuration remained unchanged and distinguish a deployment created by this run from one merely observed after an indeterminate attempt.
- Verify the live endpoint with a fresh bounded, non-mutating request and the repository-defined status or content marker when available. Record redirects or authentication limits. Provider state without a safe endpoint check is partial verification, not proof that the application works for its intended audience.
- Verify the local commit and dirty state did not change unexpectedly, enumerate generated or remaining files, and retain the exact validation plus either build results or existing-artifact integrity and provenance results used for the candidate.
- For a no-op, require evidence that the exact candidate was already the active deployment and that the live check passed. When that candidate is active but the check fails or cannot run safely, do not redeploy it; report unhealthy live verification or partial live verification respectively. For failure or partial completion, verify every completed boundary separately and identify the first unverified boundary.

## Completion report

Report the target path; provider and product; sanitized account, project or service, and environment; production or preview effect; source commit plus dirty state or artifact identity; validation plus either build or existing-artifact integrity and provenance results; reviewed provider delta and concurrency guard or limitation; preflight deployment identity; deploy command in sanitized form; post-attempt deployment or version identity, status, attribution, possible delayed side effects, and canonical URL; live-check method and result; local generated or remaining files; and every warning, stop condition, and untouched external resource. Label the outcome explicitly as deployed and verified, successful no-op, local plan only, partial completion, attribution indeterminate, or failed. Never describe repository package checks or a local plan as proof of any live deployment.
