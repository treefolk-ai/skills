# build — 构建功能

## Outcome

把用户已经说明白的一项功能需求落实为可运行、可核查的代码改动，完成适用验证，并说明实际行为和未完成之处。一次调用负责一个有界实现结果；无需用户额外声明“生产级”或“长期可维护”才应用以下默认准则。

本工作流遵循用户的两条最高实现准则：**1. 可读性优先；2. 异常优先。** 让人能顺着代码解释行为与状态；先明确真实失败如何拒绝、传播、恢复或清理，再展开正常流程。

少增实体、复用成熟能力、改善用户体验、易于删除和避免过早抽象都服务于这两条准则；不能据此降低正确性、改变已确认的契约或扩大授权。完成仍以行为证据为准。

适用于不同语言与框架；不预设目录结构、架构分层或完整产品技术栈。

## Use when

- 用户要求新增一个功能、修改一项既有行为，或将已确定的接口、页面、命令和数据处理规格落地为代码。
- 用户显式调用 `$build` 并给出预期行为；普通自然语言实现请求也适用。

典型请求：

```text
$build 给现有 CLI 增加 CSV 导出，空数据只输出表头，写入失败时返回非零退出码
$build 按已确定的接口协议实现分页查询，复用项目现有请求层
$build 给设置页增加语言选择，保存后刷新仍保留选择
```

## Do not use when

- 用户只要运行已有编译或打包命令，没有要求新增或改变代码行为。
- 用户只要代码审查、需求探索、架构取舍或实现计划，尚未要求落地代码。
- 主要目标是保持行为不变并系统性减少已有源码的重复、派生和中转；该结果属于 `context-shrink`。
- 尚需调查未知根因的故障，或需要专项性能、安全、迁移、事故处理工作流；已明确修复行为的局部实现可以使用本技能。
- 用户只要一次性实验、教学片段、伪代码或可丢弃原型。

## Inputs

- 必需：可观察的预期行为；口头需求即可，不强制先写规格文档。
- 可选：目标目录、接口或设计规格、验收条件、兼容要求、失败场景、语言与工具偏好、性能预算和验证命令。
- 默认范围：沿行为的实际调用路径寻找实现位置，只调整完成该需求必需的代码；保留未要求改变的契约和用户工作。
- 默认选择：沿用项目已确定的工具链和适用依赖；未定选项参考与项目约束兼容的用户偏好，最后使用本技能默认值。
- 缺少信息时，先读取相关上下文，再按工作流补齐必要决定；不要求用户重复提供已经可用的偏好，也不把读取记忆作为运行前提。

## Preconditions

1. 读取适用的项目说明，检查工作区已有改动；定位相关实现、调用方、公共契约、项目配置和验证入口，保留用户工作。
2. 按需读取当前会话及宿主已提供、当前任务允许访问的记忆入口中，与本次语言、工具、实现风格和协作方式相关的偏好或习惯。核对来源、适用范围和当前项目事实，区分用户明确偏好与推测；不把一次性选择推广成长期习惯。记忆缺失或不可用时使用现有上下文继续，不虚构读取结果，也不扩搜无关个人目录或外部系统。
3. 明确预期结果和保护边界；先识别本次输入、外部系统、状态和资源生命周期中的真实失败，确定拒绝、传播、恢复与清理责任，再安排正常路径。没有相关失败语义时不列假想异常。
4. 确定与改动风险相称的验证方法，利用已有结果或必要的基线检查区分既有失败与本次回归；不为小改动建立额外流程文档。

## Workflow

按以下顺序作决定，说明的篇幅随任务规模调整；不要求输出固定阶段报告或额外规划文件。

### 1. 固定行为并补齐必要决定

- 用一句话固定预期行为和完成条件，找到现有实现归属与调用路径。
- 在既定需求、正确性和兼容约束内，优先减少用户完成任务的操作与决策负担，让适用的反馈和恢复路径清楚；不因实现方便或代码更短而牺牲这些体验。只处理本次涉及的使用路径，不扩成产品重设计。
- 已有实现满足需求时，完成适用验证并返回 `NO-OP`；不为应用本技能而改代码。
- 在开始实现前，用需求、项目事实和适用偏好检查是否仍有会实质改变行为、验收、交付形态、兼容性或授权的缺口。只询问无法据此确定的必要问题，合并相关问题并简述建议与取舍；例如新项目的运行环境仍不明确，或用户希望采用的方案与项目约束冲突。
- 信息充分时，有重要选择就简述依据并继续，不例行询问技术栈或要求开工确认，不重复询问当前任务中已经明确的选择和授权。缺少一部分决定时，继续独立且已授权的工作，暂停依赖该决定的部分；未答复不代表同意。

### 2. 选择现成能力与工具

- 用户当前明确选择覆盖旧记忆和推测；普通实现任务沿用项目已确定的语言、运行时、框架和版本。项目尚未决定的选项先参考适用的用户偏好，再用本技能默认值；偏好与项目约束冲突时先查明，不以旧习惯覆盖项目事实或顺带升级、迁移。
- 先检查项目现有实现、标准库、框架原生能力和已安装依赖。对尚未满足的需求或能在本次范围内明显降低维护成本的部分，将成熟生态方案与最小局部实现一并比较，不以“手写能实现”作为排除新依赖的理由，也不重写已有可靠能力。
- 比较总维护成本：需要理解的概念、自维护代码、边界与生命周期处理、跨文件追踪，以及依赖、配置和版本兼容成本。依据实际可用版本与项目证据判断适配；不为几行稳定逻辑或仅因流行度引入一个包，不把依赖数量、代码行数当成上下文成本。
- Vue 项目涉及通用组合式逻辑时，将 VueUse 纳入候选；已有且适配的能力直接复用，不再增加没有当前收益的包装层。未采用时按上述成本判断是否值得引入，不默认安装。
- 样式实现沿用项目约定；已采用 Tailwind CSS 时复用现有 utility 与设计约束。新项目或样式方案尚未确定时，将 Tailwind CSS 纳入候选，比较样式共置、跨文件追踪与接入成本；不只按 class 数量判断可读性，不为采用它迁移当前任务之外的样式。
- 包管理器从适用项目说明、`packageManager` 声明、锁文件及 CI/脚本识别，核对它们是否一致。发现冲突时查明实际有效路径；不能确定则暂停依赖安装、锁文件更新等相关动作。
- 在没有既定包管理器、用户当前也无明确选择或适用偏好且环境兼容的 JavaScript/TypeScript 项目中默认 pnpm。这是本工作流的兜底偏好，不覆盖既有 npm、Yarn、Bun 等项目约定；其他生态使用其项目工具。
- 运行项目声明的命令并保持包管理器与锁文件一致。不得混用包管理器生成第二套锁文件；不得因偏好而迁移既有项目。工具缺失不代表可以自行安装或联网，优先完成不依赖它的安全工作并报告所缺验证。

### 3. 用最少的必要结构实现

- 异常路径先行：通过当前语言与框架的惯用机制，在适用边界用校验、守卫语句或早返回先处理无效输入与失败，让正常主路径保持清楚。只在能够恢复、补充上下文、转换边界或清理时捕获；异常优先不等于每层使用 `try/catch` 或把所有失败都转成抛异常。禁止吞错、伪造成功和没有依据的重试或降级。
- 默认在现有归属内直接实现，让一起理解和修改的逻辑靠近。简单清楚的页面、handler 或命令可以保留局部规则；函数提取不必伴随新增文件。
- **复杂性必须有当前需要，增加实体必须说明收益。** 新文件、模块、接口、状态源、配置或依赖，应解决当前可指出的行为、理解、修改、测试、复用或资源管理问题，且收益高于新增概念与跨位置追踪的成本。没有这样的收益就保留直接实现；不为未来猜测创建层、通用 helper 或插件机制。共享抽象应来自已经明确的共同规则，不只因几段代码写法相似就合并独立变化的业务规则。
- 文件长、出现多个变化原因或混有副作用只是检查信号。仅在实际边界收益成立时拆分；通过当前语言和框架的惯用机制隔离复杂业务与副作用，不强制所有入口只组装或每项职责独占文件。
- 保持主路径可顺序阅读，让输入如何成为输出、状态由谁修改、副作用何时发生可以沿直接调用路径追踪。用明确命名、局部上下文和必要的早返回降低嵌套；注释说明原因与约束，不以压缩行数牺牲可读性。
- 让功能易于替换或删除：保持专属逻辑、状态与资源清理的归属清楚，避免把特例散入无关模块或公共抽象。用“移除这个功能会牵连哪些调用方、配置和清理动作”检查耦合；不为假想替换增加接口、插件层或通用框架。
- 涉及资源、取消、超时、并发或部分写入时，采用平台的安全惯例并保持状态可解释。可恢复输入不得依赖崩溃、强制解包或未检查断言。
- 移除本次替代后已经失效的分支和重复状态；仍有兼容需求的路径保留并说明原因。发现相邻问题只报告，不借实现任务开展系统性重构。

### 4. 验证行为与改动成本

- 优先验证本次涉及的输入拒绝、外部失败、取消、恢复与清理等真实路径，再确认正常行为及适用的操作、反馈体验；可以先运行用于定位的基线或冒烟检查，必要的正常路径验证不能省略。没有适用失败路径时说明原因，不制造异常分支或无关测试。
- 运行项目要求的相关检查，按风险补充类型、lint、构建、测试或可重复的冒烟验证。低风险展示或常量改动可用相关检查或直接观察，不强制新增测试。
- 检查最终 diff：需求完整实现；主路径的行为与状态可顺序解释；新增实体有实际理由；数据没有多余的来源与中转；功能特例没有扩散到无关模块，替换或移除所需的改动归属清楚；适用错误处理明确；被替代的失效路径已移除；未覆盖用户已有改动。
- 本次引入的验证失败应修复根因后重试；范围外既有失败要有定位依据和受影响结果的独立验证。关键证据不可用时保留成果，明确缺口，不报告 `DONE`。

## Stop conditions

- 缺少会实质改变产品行为、公共契约、交付形态或失败语义的必要信息，且无法从项目事实确定。
- 需要用户尚未授权的依赖或工具安装、网络或外部系统访问、秘密修改、迁移或破坏性操作。技能选择、工具默认值、记忆中的偏好及其他任务的历史授权均不提供本次授权。
- 工作区已有改动与目标范围重叠，无法安全区分或保留。
- 实际范围显著超过原请求，继续会变成跨系统重写或专项迁移。
- 关键验证不可用，或排查后仍无法取得新证据，只能通过削弱断言、跳过适用检查、吞错或扩大未授权范围继续。

停止依赖问题前提的动作，完成其余独立且已授权的安全工作；报告精确边界、已有成果和恢复所需的最小输入或条件。

## Safety

- 不改变用户未要求改变的外部契约、业务规则、视觉行为、持久化格式或兼容范围。
- 不手改生成物、vendored 代码或锁文件；确需更新产物时使用项目生成流程，且相关动作须已获授权。
- 不覆盖用户工作；Git 提交、推送、部署和当前实现之外的外部副作用不属于本技能的默认结果或授权。
- 本技能读取相关偏好，不自动创建或改写用户记忆；需要保留新习惯时遵循当前任务的明确请求和宿主能力，不将本次选型擅自写成长期规则。
- 不记录或回显秘密；错误信息保留可诊断上下文，但不得泄露凭据、令牌或敏感载荷。

## Verification

完成前确认：

- 请求的行为可观察地成立，并且未要求改变的行为仍成立；
- 受影响的正常行为及适用失败、边界路径有证据；不适用和未运行分别说明；
- 新增结构确有当前收益，项目已有能力和工具约定得到合理复用；重要选型已比较维护成本，采用的用户偏好有来源且适用于本次任务，必要决定已在相关实现前明确；
- 相关检查没有由本次改动引入的失败，范围外既有失败有依据；
- 最终 diff 与报告一致，关键证据缺失时不宣告完成。

## Completion report

按以下互斥规则选择终态：

- `DONE`：本次完成了改动，需求和全部适用的必要验证成立。
- `NO-OP`：原有实现已满足需求，无需改动且适用验证成立。
- `PARTIAL`：已有可说明的实现进展，但需求或关键验证未全部完成；指出阻碍和剩余项。
- `BLOCKED`：尚无实现进展，缺少必要前提而无法继续；指出恢复条件。没有修改且原实现无法完成必要验证时也适用。

简述实现了什么、修改位置、验证证据和剩余事项。仅在存在重要选择时解释新增结构的收益或工具选择依据；小改动保持简短，不逐项复述本技能。
