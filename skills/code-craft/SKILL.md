# Code craft — 可持续编码

## Outcome

完成一项用户明确要求的代码成果，使它遵循当前语言、框架和仓库惯例，同时具备清晰的模块归属、直接可读的实现、显式的失败语义，以及成功与失败路径的验证证据。

通用准则只有一句：

> 可读性与失败路径优先；按变化原因拆模块，入口只组装，纯逻辑与副作用分离；多责即拆，验证成功与失败。

这是一组跨技术栈的决策标准，不是固定目录模板。合法终态为 `DONE`、`NO-OP`、`PARTIAL` 或 `BLOCKED`。

## Use when

- 用户显式调用 `$code-craft` 构建或修改产品、功能、模块、服务、组件、命令行程序或基础库。
- 用户要求从第一版开始保持代码可读、失败可控、职责清晰且长期可演进。
- 一项正常功能改动需要在局部调整边界，避免继续向已有大文件或混合职责模块堆叠代码。
- 语言或框架不同，但仍需要以其惯用机制完成同一套可维护性和验证目标。

## Do not use when

- 用户只要只读代码审查、架构讨论、问题清单或实现计划。
- 用户的主要目标是对已有范围做系统性、行为保持型上下文缩小；使用 `context-shrink`。
- 用户明确要一次性实验、教学片段、伪代码或可丢弃原型，并且不要求生产级实现。
- 目标是专项性能、安全、迁移或事故排查，且需要对应领域的专门工作流。
- 目标文件是生成物、第三方 vendored 代码、锁文件或不应手工维护的产物。

## Inputs

- 必需：可观察的代码结果，例如要新增或改变的行为、接口、页面、命令或数据处理能力。
- 可选：语言、框架、目标目录、验收条件、兼容边界、已知失败场景、性能预算和项目验证命令。
- 默认：从仓库识别技术栈与惯例；使用现有依赖；选择最小且完整的职责范围；保留用户未要求改变的外部契约和行为。
- 绿地项目若无法从请求确定语言、运行环境或交付形态，且不同选择会改变结果，只询问最小的缺失信息，不自行选定产品技术栈。

## Preconditions

1. 读取适用的项目说明、依赖与构建配置、相关模块、公共契约、测试和验证脚本；检查工作区已有改动并保留用户工作。
2. 明确本次可观察结果、负责该结果的模块、不能改变的契约，以及可信输入、外部边界和资源生命周期。
3. 在编码前列出真实失败类别及其处理方式：拒绝、返回、传播、恢复、重试、降级或向用户呈现。不要为没有证据的假想异常增加分支。
4. 确定最小相关验证集合。小改动保持轻量；跨模块或高风险改动需要更完整的成功、失败和边界验证。

## Workflow

按 `FRAME → SHAPE → IMPLEMENT → VERIFY` 推进，并按任务规模调整展开程度；小改动不制造仪式，大改动不跳过边界判断。

### 1. FRAME

- 用一句话固定预期行为和完成条件。
- 找到真正拥有该行为的模块，不把新逻辑默认放进入口文件、页面、控制器、handler、`main`、App 或全局工具文件。
- 确认正常路径、失败路径和不可破坏的既有行为。已有实现已经满足结果时直接验证并返回 `NO-OP`。

### 2. SHAPE

- 按变化原因组织代码：共同变化的逻辑靠近，不同原因变化的职责分开；优先高内聚、低耦合的边界。
- 入口层负责组装和调度；业务规则保持可独立理解和测试；网络、数据库、文件、时钟、随机数、系统 API 与 UI 生命周期等副作用集中在边界。
- 遵循当前生态的惯用写法，而不是跨语言照搬目录、类层次或错误模型。使用 `error`、`throws`、`Result`、异常或联合类型时，以目标语言惯例为准。
- 优先直接代码和项目已有能力。只有抽象能减少重复决策、稳定边界或形成真实复用时才引入；不为未来猜测创建层、接口、helper 或配置。
- 文件长度只是检查信号。一个文件出现第二个独立变化原因时拆分；单一职责仍清晰时，不为满足行数制造碎片和转发层。

### 3. IMPLEMENT

- 先写清边界校验和失败语义，再保持主路径笔直。优先早返回、浅嵌套、明确命名和局部上下文。
- 错误必须被处理、显式传播或转换；只在能够恢复、补充上下文、转换边界或完成清理时捕获，禁止吞错和伪造成功。
- 对资源、并发、取消、超时和部分写入采用当前平台的安全惯例；可恢复输入不得依赖崩溃、强制解包、`panic` 或未检查断言。
- 注释解释原因、约束和不变量，不复述代码。若需要长注释才能解释流程，先改善命名、控制流或模块边界。
- 用新实现替代旧路径时同步移除已失效分支；不让新旧两套实现、重复状态或临时兼容层无期限并存。
- 只修改完成当前结果所需的代码。发现相邻问题时记录，不顺手扩大任务。

### 4. VERIFY

- 先运行最相关的测试或检查，再按风险运行类型检查、静态检查、lint、构建和必要的冒烟验证。
- 至少验证一个成功路径和一个真实失败路径；存在边界值、权限、取消、超时、重试、并发或部分状态时，验证适用项。
- 检查最终 diff：模块各有清晰归属，入口没有吸收业务细节，错误没有被吞掉，旧实现没有残留，用户已有改动和范围外文件未被覆盖。
- 关键验证失败时只修复与本次结果有关的根因并重试；不能证明结果时不得报告 `DONE`。

## Stop conditions

- 缺少会实质改变产品行为、公共契约或失败语义的必要信息。
- 正确实现必须作出用户尚未授权的产品、数据、兼容性或系统架构决定。
- 需要新增生产依赖、访问网络或外部系统、修改秘密、执行迁移或采取破坏性操作，而当前请求没有覆盖该动作。
- 工作区已有改动与目标范围重叠，无法安全区分或保留。
- 实际范围显著超过原请求，继续会变成跨系统重写或专项迁移。
- 关键验证不可用、连续失败，或只能通过削弱断言、跳过失败路径、吞错或扩大未授权范围才能通过。

停止时保留可验证的安全进度，报告精确边界、已完成与未完成内容，以及恢复所需的最小决定。

## Safety

- 不把“通用规范”变成固定框架架构；项目惯例和语言习惯优先，除非它们直接造成当前问题。
- 不因文件较长就机械拆分，不用空壳模块、单次转发、无意义接口或 `utils` 垃圾抽屉置换原有复杂度。
- 不改变用户未要求改变的外部契约、业务规则、视觉行为、持久化格式或兼容范围。
- 不覆盖用户工作，不修改 Git 历史，不提交、不推送、不部署，也不执行当前代码结果之外的外部副作用。
- 不记录或回显秘密；错误信息保留可诊断上下文，但不得泄露凭据、令牌或敏感载荷。

## Verification

完成前确认：

- 请求的行为可观察地成立，并且未要求改变的行为仍成立；
- 成功、失败及适用边界路径有测试或可重复验证证据；
- 每个新增或显著修改的模块都能用一个主要变化原因解释；
- 主路径可顺序阅读，失败处理明确，没有不必要嵌套、隐式状态和聪明但晦涩的抽象；
- 项目提供的相关类型、静态、lint、测试和构建检查没有新增失败；
- 无法运行的检查被明确标为未运行，且关键证据缺失时结果标记为 `PARTIAL` 或 `BLOCKED`。

## Completion report

以 `DONE`、`NO-OP`、`PARTIAL` 或 `BLOCKED` 开头，报告：

- 完成的可观察行为和实际修改范围；
- 模块边界及关键职责为何放在当前位置；
- 已处理的失败类别、传播方式与用户可见结果；
- 运行过的验证命令、成功与失败路径证据、未运行项；
- 保留的外部契约、用户已有改动、范围外发现和剩余风险。
